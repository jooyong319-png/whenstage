# 결정 기록

## 왜 gcalen을 접고 새로 시작했나 (2026-07-21)
사용자가 다니는 회사가 gcalen과 거의 동일한 컨셉(게임 정보·쿠폰으로 유저를 모으는
캘린더 서비스, "쌀먹닷컴")을 사내에서 준비 중이었음. gcalen을 회사 동료에게
소개했는데 회사가 비밀유지계약서(겸업금지·기밀유출 조항)를 근거로 gcalen 운영
중단을 요청. 사용자가 수용해 gcalen 서비스는 닫기로 함(저장소는 비공개 전환
예정, 코드는 보존).

다만 `gcalen.com` 도메인과 Vercel 프로젝트는 사용자 소유이므로 재사용하기로
하고, 완전히 다른 주제로 사이트를 새로 만들기로 함.

## 왜 콘서트/음원 발매 캘린더인가
후보 2개 중 선택:
1. 쇼핑/이커머스 세일 캘린더 — 탈락. "쿠폰/딜로 유저를 모은다"는 메커니즘이
   이번에 문제 됐던 것과 똑같아서 회사와 또 비슷한 마찰이 생길 위험이 있음.
2. **콘서트·내한·음원 발매 캘린더 — 채택.** 쿠폰 개념이 아예 없는 순수 일정
   추적이라 회사 사업과 겹치지 않고, K팝 팬덤의 해외 검색 수요가 커서 글로벌
   SEO 확장에도 유리함.

## 왜 쿠폰/게임 허브 기능을 통째로 제거했나
gcalen에는 `data/coupons.json` 기반 쿠폰 카탈로그·게임 허브(`/coupons`,
`/games/[key]`) 기능이 있었는데, 이게 바로 회사와 마찰이 생긴 "정보+쿠폰으로
유저 모으기" 메커니즘 그 자체였음. 새 프로젝트에서는 이 패턴을 완전히
배제하기 위해 관련 코드(`lib/coupons.ts`, `lib/game-hub.ts`,
`components/CouponList.tsx`, `/coupons`, `/games` 라우트)를 전부 삭제.
쿠폰 없이 순수 "일정 추적 + 알림"만 남김.
whenstage에서는 쿠폰 없이 순수 "일정 추적 + 알림"만 남겼다.

### ⚠️ 위 두 항목의 차단 사유 정정 (2026-07-29)
원래 여기에 **"정보+쿠폰/딜로 유저 모으기 패턴을 앞으로도 절대 넣지 않는다"** 고 적어
두었는데, **원인을 잘못 지목한 규칙이었다.** 사용자 확인 결과:

- 사용자가 다니는 회사가 곧 **게임 정보 커뮤니티 "쌀먹닷컴"** 이다. 마찰이 생긴 실제 이유는
  gcalen이 **"게임"이라는 콘텐츠 버티컬을 공유해** 직접 경쟁 사이트가 되기 때문이었다.
  **쿠폰이라는 메커니즘 자체가 문제였던 게 아니다.**
- 계약서에 **겸업금지 조항은 없다.** gcalen은 회사 기술을 쓰지 않고 독자 개발한 것이다.

따라서 정확한 규칙은 이렇다:
- ❌ **게임 관련 콘텐츠로 서비스를 만들지 않는다** (회사 사업과 직접 경쟁하게 됨)
- ⭕ 쿠폰·딜·어필리에이트 메커니즘 자체는 **다른 버티컬에서는 문제되지 않는다**

whenstage에서 쿠폰 기능을 뺀 것은 이 프로젝트가 순수 일정 서비스로 정해졌기 때문이고,
"쿠폰은 영구 금지"라는 뜻이 아니다. 잘못된 일반화가 이후 기획을 막고 있었으므로 정정한다.
(예: 쇼핑/이커머스 세일 캘린더는 게임과 무관한 버티컬이라 이 사유로는 배제되지 않는다.)

검증된 뒤 별도 리팩터링으로 미룸. **아직도 유효한 판단 — 필드명 리네임은
우선순위 낮음, 섣불리 손대지 말 것.**

## ko/en/ja는 번역이 아니라 완전히 독립된 데이터다 (2026-07-21~)
초기엔 gcalen 방식(한국어 원본 + en/ja 선택적 번역)을 검토했으나, 실제로 한국
공연과 미국/일본 공연은 서로 다른 실사 이벤트라 "번역"이라는 개념 자체가
안 맞는다고 판단해 완전 독립 데이터 구조로 확정. `data/concerts.ko/en/ja.json`은
각자 다른 실제 공연을 담고, 리서처 3명이 각자 자기 언어권만 담당(자세한 내용은
`AGENTS.md`). 이후 뉴스(`content/news/`)도 같은 원칙으로 리팩터링, 아티스트
프로필(`data/artist-images.json`/`artist-bios.json`)도 로케일별 독립.

**블로그(모아보기)도 결국 같은 원칙으로 전환(2026-07-22)** — 처음엔 "번역해도 의미가
통하는 콘텐츠라 굳이 3배로 따로 쓸 필요 없다"고 KO 원본 + 선택적 EN/JA 번역 구조로 예외를
뒀었으나, 다른 모든 콘텐츠가 로케일별 독립인데 블로그만 예외인 게 일관성이 떨어진다고
판단해 철회. `content/blog/<slug>.ko.md`/`.en.md`/`.ja.md`로 파일명 규칙을 뉴스와 동일하게
바꾸고, 각 로케일 담당(`prompts/BLOG_RESEARCHER_KO/EN/JA.md`)이 자기 언어권 콘서트 데이터로
독자적인 소재를 골라 쓴다 — 번역이 아니라 완전히 다른 글일 수 있음. 이 결정 당시 블로그
글은 KO 1건뿐이라 마이그레이션 부담 없이 바로 전환.

## 아티스트/공연장 허브 페이지는 콘서트 이미지에서 분리 관리 (2026-07-22)
아티스트 대표 이미지를 처음엔 콘서트 엔트리의 `image_url`에서 재활용했는데,
행사 스냅샷(레드카펫 단체샷 등)이 그대로 대표 이미지가 되는 품질 문제가 있어서
`data/artist-images.json`/`artist-bios.json`으로 완전히 분리. 공연장 페이지
(`/venue`)는 `platforms` 필드를 정규화해 그룹핑하는 방식으로 별도 데이터 파일 없이 구현.

## 콘텐츠 자동화와 기획/개발 자동화는 완전히 분리한다 (2026-07-22)
- **콘텐츠 파이프라인**(리서처 6종 + `prompts/ARTIST_PROFILE.md` + `prompts/BLOG_RESEARCHER_KO/EN/JA.md`): 정해진
  스키마 안에서 데이터/글을 채우는 작업이라 자동 실행 리스크가 낮음. `prompts/PLANNER.md`가 주 1회
  신호(블로그 최신성, 아티스트 프로필 커버리지)를 점검해 필요하면 위 두 개를 대신 실행.
- **기획/개발 파이프라인**(`prompts/PRODUCT_PLANNER.md` + `prompts/PRODUCT_DEVELOPER.md`): 실제 코드·UI·
  기능을 바꾸는 작업이라 리스크가 다름. 콘텐츠 데이터는 절대 건드리지 않고, 이 위키를
  반드시 먼저 읽고 시작한다.
- `prompts/PLANNER.md`와 `prompts/PRODUCT_PLANNER.md`는 이름이 비슷하지만 역할이 다르다 — 헷갈리지 말 것.

## 2차 디자인 오버홀 — 색은 "라이트=모노, 다크=레이저 워시" (2026-07-23)
1차 오버홀(2026-07-22~23)에서 정한 핑크→보라 그라데이션 + Space Grotesk + pill(999px) 라운드
조합을, 오너가 "모던하고 현대적인 느낌"을 원한다고 밝히면서 다시 갈아엎었다. 재검토 과정에서
그 조합 자체가 문제였다는 게 드러남 — 흰 배경 위 보라 계열 그라데이션 히어로, 무난한 지오메트릭
디스플레이 폰트, 어디에나 붙는 pill 라운드는 AI가 별생각 없이 뽑는 "기본값"에 가장 가까운
조합이었다. 그래서 유행을 더 얹는 대신 콘서트라는 소재 자체(무대 조명, 티켓의 물성)에서
재료를 가져오기로 함.

색 후보 4개(리소 포스터=종이+리소블루, 커튼콜=마룬+스칼렛, 레이저 워시=네이비+시안,
모노+의미색=순흑백+카테고리색만)를 시안으로 제안했고, 오너가 **다크 모드=레이저 워시,
라이트 모드=모노**로 조합해서 가자고 결정. 근거: 다크는 공연 당일 저녁에 몰입해서 보는
상황, 라이트는 낮에 빠르게 확인·캡처·공유하는 상황이라 실제 두 사용 맥락과 맞아떨어짐.
라이트 모드는 액센트 색 자체가 없는 대신(잉크=검정이 곧 액센트) "시간에 민감한 정보"
(공연일·D-day·예매 시각)에만 별도의 `--accent-warm`(호박색 계열, 테마 공통)을 씀 — 이건
브랜드 액센트가 아니라 의미색이라 모노 컨셉과 충돌하지 않는다는 판단.

형태도 함께 바꿈: pill(반경 999px)을 어디에나 쓰던 것을 3/6/10/16px "티켓 스텁" 스케일로
좁히고, 블러 그림자 의존을 줄이고 실선 보더·점선 절취선을 1차 구획 수단으로 삼았다.
디스플레이 서체(Space Grotesk)는 제거하고 이미 프로젝트에 있는 Pretendard Variable을
굵기 축(45~920)만으로 본문/디스플레이 겸용으로 쓴다 — 폰트 패밀리가 하나로 줄어 로딩
부담도 줄고, "안전한 지오메트릭 서체"라는 상투성에서도 벗어남. 숫자(날짜·D-day·타임존)는
시스템 모노스페이스(`--font-mono`)로 분리해 전광판/티켓 인쇄 느낌 + 자릿수 정렬을 확보.

**같은 작업 범위에서 기술부채도 함께 정리**(오너가 명시적으로 "같이 정리" 선택) — gcalen
잔재 죽은 CSS/타입(`EventType`의 `game_show` 등), orphan 컴포넌트 7종, 미정의 CSS 변수,
카드 컴포넌트 보더 규칙 불일치를 이번 커밋 범위에 함께 넣음. 자세한 배경은
[[design-audit]], 실제 변경 내역은 `PROJECT_STATUS.md` 2026-07-23 항목 참고.

## html lang을 멀티 루트 레이아웃으로(단순 미들웨어 헤더 방식은 기각) (2026-07-23)
SEO 감사 중 `<html lang="ko">`가 전 로케일에 고정 렌더링되고(클라이언트 스크립트가 뒤늦게
패치) JS 미실행 크롤러/번역기엔 잘못된 값이 보인다는 문제를 발견. 두 가지 해결책을
검토했다:
1. 미들웨어에서 로케일을 감지해 요청 헤더로 넘기고, 루트 레이아웃이 `headers()`로 읽어서
   `<html lang>`을 동적으로 렌더링 — **기각**. `headers()` 사용은 그 라우트 전체를 강제로
   동적 렌더링(SSR)으로 전환시켜, 이 사이트 전체가 의존하는 정적 생성(SSG)을 깨버린다.
   SEO를 고치려다 오히려 Core Web Vitals·서버 비용을 악화시키는 트레이드오프라 기각.
2. **Next.js 멀티 루트 레이아웃(route group)으로 전환 — 채택.** `app/(locale)/[lang]/layout.tsx`가
   `params.lang`으로 서버에서 직접 `<html lang>`을 렌더링하고, SSG는 그대로 유지된다.
   대신 로케일 없는 나머지 라우트(admin, 바닥 `/` 리다이렉트, 전역 404/에러)를 위한
   `app/(app)/layout.tsx`가 별도로 필요해서 라우팅 구조가 두 그룹으로 나뉘었다(자세한
   구조는 [[architecture]]). 이 작업 중 "라우트 그룹은 not-found/error 경계를 못 넘는다"는
   함정에 실제로 걸려서(고쳤더니 존재하지 않는 콘서트 id에서 무스타일 에러 화면이 뜸)
   두 그룹 다 자체 `not-found.tsx`/`error.tsx`/`loading.tsx`를 갖게 됐다.

## 검색 아티스트 별칭 — 자동 음역 대신 큐레이션 테이블 (2026-07-23)
"bigbang으로 검색해도 빅뱅이 나오게 해달라"는 요청에 규칙 기반 자동 로마자 변환을
검토했으나 기각 — 케이팝 그룹은 "방탄소년단→BTS", "아이유→IU"처럼 발음과 무관한 영문
활동명을 쓰는 경우가 대부분이라 규칙 변환이 근본적으로 안 맞는다. 대신
`data/artist-aliases.json`에 검증된 영문/로마자 표기만 수동으로 큐레이션(대부분은 이미
`data/artist-bios.json`에 검증돼 있던 표기를 재사용). 확신 없는 로마자 표기는 아예 안
넣는 게 원칙 — 틀린 정보보다 없는 게 낫다. 새 아티스트 추가 시 이 파일도 같이 챙길 것
(리서처 프롬프트가 자동으로 채우지 않음, 수동 큐레이션 대상).

## 선예매 마감 판정 — 일반예매 시작을 폴백으로 (2026-07-23)
`presale_end_datetime`이 없는 실전 데이터가 많은데(마감일을 따로 공지 안 하는 경우),

## 목록 진입점은 모달이라도 반드시 `<a href>` (2026-07-28)
캘린더·목록·카드의 상세 진입점이 전부 `<button onClick>` + 모달이었다. UX는 문제없었지만
**서버 HTML에 `/[lang]/concert/<id>` 링크가 하나도 안 남아** 크롤러가 상세 페이지를 고아로
취급했다. 실측: ko 콘서트 상세 34개 중 **11개가 어디서도 링크되지 않는 URL**(사이트맵에만 존재).
→ `GameRow`/`ScheduleCard`/`UpcomingStrip`의 진입점을 상세 페이지를 가리키는 `<a>`로 바꾸고
클릭에서 `preventDefault()`로 가로채 모달을 띄운다. 수식어 키(meta/ctrl/shift/alt)는 통과시켜
새 탭 열기를 살린다. 결과 11개 → 0개.
- **재발 방지**: 목록·카드 UI를 새로 만들 때 상세 진입점은 항상 `<a href>`. `prompts/PRODUCT_DEVELOPER.md`
  §4에도 같은 규칙과 코드 스니펫을 넣어 뒀다.
- CSS는 `text-decoration:none`만 추가하면 기존 버튼 스타일이 그대로 산다.

## 저품질 페이지 색인 제외 기준 — `events.length >= 2` (2026-07-28)
공연장/아티스트 상세가 공연 1건뿐이면 그 공연 상세와 내용이 사실상 같아 검색엔진에 중복으로
남는다(서치 콘솔에서 "크롤링됨 – 색인 생성 안 됨"으로 쌓이던 URL 다수가 이 케이스).
→ `isVenueIndexable`(venues.ts) / `isArtistIndexable`(artists.ts)로 판정해 `noindex, follow` +
사이트맵 제외. 사이트맵 394 → 300.
- **기각한 대안**: `upcomingCount === 0`(지난 공연만 있는 것)만 제외 — 실측해보니 ko/en/ja
  통틀어 15건뿐이라 효과가 없었다. 실제 대량 발생 지점은 "공연 1건짜리"였다.
- 아티스트는 예외를 뒀다: 큐레이션 소개문(`bio`)이 있으면 일정이 1건이어도 고유 텍스트가 있으므로 색인 유지.
- **중요**: 상세가 noindex인데 사이트맵에는 올리면 크롤러에 모순 신호라 서치 콘솔에 오류로 쌓인다.
  두 곳이 같은 판정 함수를 쓰도록 강제할 것.

## 구조화 데이터는 "아는 만큼만" — endDate·organizer.url (2026-07-28)
서치 콘솔 "항목 표시 개선"(경고, 오류 아님) 대응하면서 정한 원칙: **경고를 없애려고 없는 사실을
만들지 않는다.**
- `endDate`: 다일 공연은 마지막 날, **시각을 모르는(날짜만 아는) 공연은 그 날짜를 종료일로** 채운다
  (구글 문서가 하루짜리 행사는 startDate=endDate를 권장). 시작 시각까지 아는 공연은 끝나는 시각을
  알 수 없어 **생략**한다. *기각한 대안*: 임의로 3시간쯤 더해 채우기 — 검색결과에 없는 사실이 나간다.
- `organizer.url`: 원래 우리 페이지 주소(`eventUrl`)가 들어가 있었다. 주최사 URL 자리에 whenstage를
  넣는 건 **틀린 표기**라 제거했다. *트레이드오프*: 이 경고는 오히려 늘지만 정확성을 택했다.
- `startDate`: 오프셋 없이 `2026-08-07T19:00`로 나가면 구글이 시간대를 모른다. 항목마다 IANA
  `timezone`이 있으므로 `lib/seo.ts`의 `eventStartDate()`가 **그 날짜 기준 오프셋**을 계산해 붙인다
  (DST 지역은 계절에 따라 오프셋이 달라 고정값으로는 안 된다). 판정 실패 시 오프셋 없이 물러난다.

## 사이트맵 `lastmod`는 빌드 시각이 아니라 콘텐츠 변경일 (2026-07-28)
정적 페이지·아티스트·공연장에 `lastModified: new Date()`(빌드 시각)를 넣고 있었다. 배포만 해도
**394개 중 224개가 "오늘 수정됨"** 이 되어, 구글이 lastmod 자체를 신뢰하지 않게 된다.
→ 로케일별 `last_updated`(데이터 파일)와 글 날짜를 쓰고, 약관·소개처럼 배포와 무관한 페이지는
**lastmod를 아예 생략**한다. 적용 후 "오늘 날짜" 0개.

## Next.js는 14.2.x 패치까지만 — 16 이전은 별건 (2026-07-28)
